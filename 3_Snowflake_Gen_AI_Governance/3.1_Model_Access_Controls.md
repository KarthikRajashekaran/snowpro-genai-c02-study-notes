# 3.1 Model Access Controls

This section covers how to control **which models can be used**, how to **secure inference**, and how to reduce **hallucinations and bias** — objective 3.1 of the C02 exam. Governance is layered: an **account allowlist** decides which models exist, **RBAC / application roles** decide who may call them, and **guardrails, redaction, and cross-region settings** decide how safely inference runs.

## Layer 1: Restricting Which Models Can Be Used

### Account-Level Allowlist — `CORTEX_MODELS_ALLOWLIST`

`CORTEX_MODELS_ALLOWLIST` is an **account-level parameter** that limits which LLMs any Cortex function (`COMPLETE`, `AI_COMPLETE`, etc.) is permitted to invoke. Only an account administrator (`ACCOUNTADMIN`) can set it.

```sql
-- Allow only two specific models account-wide
ALTER ACCOUNT SET CORTEX_MODELS_ALLOWLIST = 'mistral-large2,llama3.1-70b';

-- Allow every supported model
ALTER ACCOUNT SET CORTEX_MODELS_ALLOWLIST = 'All';

-- Block all models (no Cortex LLM inference permitted)
ALTER ACCOUNT SET CORTEX_MODELS_ALLOWLIST = 'None';

-- Inspect the current setting
SHOW PARAMETERS LIKE 'CORTEX_MODELS_ALLOWLIST' IN ACCOUNT;
```

You can scope a model to a **specific role** using the `model:role` form, so that only members of that role may use it:

```sql
-- Everyone may use mistral-large2; only ANALYST_RW may use claude-3-5-sonnet
ALTER ACCOUNT SET CORTEX_MODELS_ALLOWLIST = 'mistral-large2,claude-3-5-sonnet:ANALYST_RW';
```

> **Exam tip:** The allowlist controls *which models are callable*, not *who can call Cortex at all*. Access to the Cortex functions themselves is governed by the `SNOWFLAKE.CORTEX_USER` database role (see 3.2). Both layers must pass.

### Application Roles and RBAC

Beyond the allowlist, model and feature access is controlled by **Role-Based Access Control (RBAC)**:

- **Database roles** (e.g., `SNOWFLAKE.CORTEX_USER`) gate access to the Cortex functions and services — covered fully in [3.2](./3.2_RBAC_Roles_and_Privileges.md).
- **Application roles** are exported by Snowflake Native Apps and by managed features; you `GRANT`/`REVOKE` an application role to an account role to expose or hide the underlying capability.

```sql
-- Expose an application role's capability to a specific account role
GRANT APPLICATION ROLE my_ai_app.app_user TO ROLE data_science_rw;

-- Remove it later
REVOKE APPLICATION ROLE my_ai_app.app_user FROM ROLE data_science_rw;
```

The governance pattern is: **grant the narrowest role to the narrowest audience**, then use the allowlist to bound the model surface.

## Layer 2: Data Safety & Security

### Cross-Region Inference

By default, a Cortex request can only run against a model **hosted in your account's own region**. If a requested model is not available locally, the request fails — unless **cross-region inference** is enabled. The account parameter `CORTEX_ENABLED_CROSS_REGION` controls this, and it is **disabled by default**.

```sql
-- Allow Snowflake to route inference to any region (data may cross regions)
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'ANY_REGION';

-- Restrict routing to a specific cloud/region group only
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'AWS_US';

-- Disable cross-region routing (default)
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'DISABLED';
```

> **Governance note:** Cross-region inference may move prompt/response data outside the account's home region. Data-residency-sensitive workloads should keep it `DISABLED` or restrict it to an approved region group.

### Guardrails / Cortex Guard

**Cortex Guard** filters potentially harmful, unsafe, or policy-violating model output (it uses Meta's Llama Guard under the hood). Enable it via the `guardrails` option on the completion function:

```sql
-- Enable Cortex Guard on a completion; unsafe responses are filtered out
SELECT SNOWFLAKE.CORTEX.COMPLETE(
    'mistral-large2',
    [ {'role': 'user', 'content': 'Draft a customer response about a refund'} ],
    {'guardrails': true}
) AS safe_response;
```

With `AI_COMPLETE`, pass guardrails through the model options argument in the same way. When Cortex Guard blocks a response, the function returns a filtered/empty result rather than the unsafe content.

### Sensitive Data Management with `AI_REDACT`

`AI_REDACT` detects and masks sensitive information (PII such as names, emails, phone numbers, and account identifiers) in text before it is stored, displayed, or sent to a model. Use it to keep sensitive values out of prompts and logs.

```sql
-- Redact PII from free-text before feeding it into a prompt
SELECT AI_REDACT(
    'Contact John Doe at john.doe@example.com or 555-123-4567'
) AS redacted_text;

-- Redact a column at load time
SELECT
    ticket_id,
    AI_REDACT(customer_message) AS redacted_message
FROM support_tickets;
```

Pair `AI_REDACT` with **masking policies** and **tag-based masking** for defense in depth: redact inside AI pipelines, and mask at the column level for everyone else.

## Layer 3: Reducing Hallucinations and Bias

The exam expects concrete Snowflake-native mitigations, not abstract ethics controls:

| Technique | How it reduces hallucination / bias |
|-----------|-------------------------------------|
| **Grounding / RAG** | Retrieve authoritative context (Cortex Search / vector similarity) and pass it into the prompt so the model answers from your data, not its training memory. |
| **Verified queries** | In Cortex Analyst, curate a **verified query repository** so natural-language questions map to known-correct SQL instead of improvised queries. |
| **Fine-tuning** | Adapt a base model on domain data to reduce off-distribution guesses. |
| **Lower temperature** | Set `temperature` near `0` for deterministic, less "creative" (less hallucination-prone) output. |
| **Cortex Guard** | Filters unsafe/biased output before it reaches the user. |

```sql
-- Grounded generation: answer strictly from retrieved context, low temperature
SELECT SNOWFLAKE.CORTEX.COMPLETE(
    'llama3.1-70b',
    CONCAT(
        'Answer ONLY from the context. If not present, say you do not know.\n',
        'Context: ', retrieved_context, '\n',
        'Question: ', user_question
    ),
    {'temperature': 0}
) AS grounded_answer
FROM rag_inputs;
```

## Layer 4: REST API Authentication

The Cortex REST API (used by Cortex Analyst, Agents, Search, and Inference endpoints) supports three authentication methods. Choose based on whether the caller is a service or a user:

| Method | Use case | Notes |
|--------|----------|-------|
| **Key-pair (JWT)** | Service-to-service / machine callers | Generate an RSA key pair, register the public key on the Snowflake user, sign a **JWT** and exchange it for access. No interactive login. |
| **OAuth** | User-delegated access via an identity provider | Standard OAuth 2.0 bearer token; supports SSO/IdP integration. |
| **PAT (Programmatic Access Token)** | Simple token-based access for a user/role | A **Programmatic Access Token** scoped to a role; convenient for scripts and CI. |

```text
# Bearer token is sent in the Authorization header regardless of method
POST https://<account>.snowflakecomputing.com/api/v2/cortex/inference:complete
Authorization: Bearer <JWT | OAuth token | PAT>
Content-Type: application/json
```

> **Exam tip:** Key-pair JWT is the go-to for **unattended/service** integrations; OAuth is for **user-delegated** IdP flows; PAT is a lightweight per-role token. Never embed credentials in code — reference them from a secret store.
