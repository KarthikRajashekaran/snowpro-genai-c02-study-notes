# 2.5 Chat Interfaces, Pipelines & Third-Party Models

This page covers three C02 sub-objectives:

## 2.3 Build or interact with chat interfaces

### Set up the environment & required privileges
To call Cortex functions and build chat apps, a role needs:
- **`SNOWFLAKE.CORTEX_USER`** database role — grants access to Cortex LLM/AISQL functions. (Grant it to your role; it is granted to `PUBLIC` by default in many accounts but is often restricted.)
  ```sql
  GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE analyst_role;
  ```
- **`USAGE`** on the warehouse that runs the queries, and `USAGE`/`SELECT` on the databases, schemas and tables the app reads.
- For **Cortex Search**: `USAGE` on the search service (and `CREATE CORTEX SEARCH SERVICE` to build it). For **Cortex Analyst**: access to the semantic model/view and (via the app) the Analyst REST endpoint.
- For **Streamlit in Snowflake**: privileges to create/run a Streamlit object in a schema.

### Invoke Cortex functions in app code (Streamlit in Snowflake)
**Streamlit in Snowflake (SiS)** hosts a Python app inside Snowflake, running with the app's role — ideal for chat UIs because Cortex calls stay in-account with no data egress. Two ways to call Cortex from Python:

```python
import streamlit as st
from snowflake.snowpark.context import get_active_session
from snowflake.cortex import complete          # Python wrapper for AI_COMPLETE

session = get_active_session()

# Option A: Python API
answer = complete("claude-3-5-sonnet", user_question, session=session)

# Option B: just run SQL from the app
answer = session.sql(
    "SELECT AI_COMPLETE(?, ?)", params=["llama3.1-70b", user_question]
).collect()[0][0]

st.write(answer)
```

### Multi-turn architecture & the role of memory
LLMs are **stateless** — the model does not remember prior turns. **Memory = maintaining conversation context across requests**, which you implement by **keeping a `messages` array** and resending the whole (growing) history on each call. In Streamlit, store it in `st.session_state`:

```python
if "messages" not in st.session_state:
    st.session_state.messages = [
        {"role": "system", "content": "You are a helpful data assistant."}
    ]

if prompt := st.chat_input("Ask a question"):
    # 1) append the user's new turn
    st.session_state.messages.append({"role": "user", "content": prompt})

    # 2) send the FULL history so the model has context ("memory")
    reply = complete("llama3.1-70b", st.session_state.messages, session=session)

    # 3) append the assistant turn so it persists for the next request
    st.session_state.messages.append({"role": "assistant", "content": reply})
```

Key ideas the exam tests:
- **Update parameters via the messages array** — you extend `messages` with each `{role, content}` turn; conversation history lives there, not in the model.
- Trim/summarize old turns to stay within the context window on long chats (e.g. summarize early turns with `AI_COMPLETE`).
- For RAG chat, retrieve context (Cortex Search) each turn and inject it into the latest user message.

### Snowflake Intelligence
**Snowflake Intelligence** is Snowflake's built-in, agentic natural-language experience for chatting with your data. A **Cortex Agent** orchestrates tools — **Cortex Analyst** (structured/text-to-SQL) and **Cortex Search** (unstructured/RAG) — and can call AISQL functions, planning multi-step answers over both data types. It gives business users a chat UI with memory, citations, and suggested questions **without building a custom app** — the managed alternative to a hand-built Streamlit chatbot.

## 2.4 Apply Cortex functions in data pipelines

Because AISQL functions are **just SQL**, they drop straight into ELT/ETL pipelines (dbt models, Streams & Tasks, Dynamic Tables, Snowpark). The **SQL interface** makes AI a set-based transformation over rows.

Common pipeline roles:
- **Extraction** — `AI_PARSE_DOCUMENT`, `AI_EXTRACT`, `AI_TRANSCRIBE` turn unstructured files into columns.
- **Enrichment** — `AI_CLASSIFY`, `AI_SENTIMENT`, `AI_TRANSLATE` add derived attributes to each row.
- **Augmentation** — `AI_COMPLETE` (structured outputs) generates new fields (summaries, tags, normalized values); `AI_EMBED` adds vectors for search.
- **Transformation** — `AI_FILTER` keeps relevant rows; `AI_AGG` / `AI_SUMMARIZE_AGG` roll many rows into insights.

```sql
-- A Task that enriches new support tickets on a schedule
CREATE OR REPLACE TASK enrich_tickets
    WAREHOUSE = etl_wh
    SCHEDULE  = '5 MINUTE'
AS
INSERT INTO tickets_enriched
SELECT
    t.id,
    AI_CLASSIFY(t.body, ['billing','technical','account','other'])       AS category,
    AI_SENTIMENT(t.body)                                                  AS sentiment,
    AI_COMPLETE('llama3.1-8b', 'One-line summary: ' || t.body)            AS summary,
    AI_REDACT(t.body)                                                     AS redacted_body
FROM raw_tickets_stream t;      -- a Stream feeding only new rows
```

Best practices: use `TRY_COMPLETE` for fault tolerance in batch; process incrementally with **Streams** so you only pay for new rows; pre-check length with `AI_COUNT_TOKENS`; pick the smallest adequate model.

## 2.5 Run third-party models

When you need a model **not** offered as a managed Cortex function (a custom/open-source model, a specialized fine-tune), Snowflake offers two paths.

### Snowpark Container Services (SPCS)
Run **containerized** models (any language, GPU-capable) fully inside Snowflake. Setup steps:

1. **Environment setup** — role with privileges to create compute pools, image repositories and services; a database/schema to hold them.
2. **Docker image** — package the model + inference server (e.g. FastAPI/vLLM) into a container image.
3. **Image repository** — create one in Snowflake and **push** the image:
   ```sql
   CREATE IMAGE REPOSITORY my_repo;
   -- docker login <org>-<account>.registry.snowflakecomputing.com
   -- docker push  <...>/my_repo/my_model:latest
   ```
4. **Compute pool** — provision the compute (CPU/GPU nodes) the service runs on:
   ```sql
   CREATE COMPUTE POOL model_pool
       MIN_NODES = 1 MAX_NODES = 2
       INSTANCE_FAMILY = GPU_NV_S;
   ```
5. **Service spec file** — a YAML describing containers, the image, ports, endpoints and resources:
   ```yaml
   spec:
     containers:
       - name: model
         image: /db/schema/my_repo/my_model:latest
         resources:
           requests: {nvidia.com/gpu: 1}
     endpoints:
       - name: predict
         port: 8080
         public: false
   ```
   ```sql
   CREATE SERVICE my_model_service
       IN COMPUTE POOL model_pool
       FROM SPECIFICATION $$ ...spec above... $$;
   ```
6. **Call it** — expose the service function and invoke from SQL like any UDF.

### Snowflake Model Registry
The **Model Registry** (part of Snowpark ML) versions and serves models as first-class schema objects. Two operations to know:

**Log the model:**
```python
from snowflake.ml.registry import Registry
reg = Registry(session, database_name="ML_DB", schema_name="MODELS")

mv = reg.log_model(
    model,                       # sklearn/xgboost/pytorch/HF/etc.
    model_name="churn_clf",
    version_name="v1",
    conda_dependencies=["scikit-learn"],
    sample_input_data=train_df   # infers the signature
)
```

**Call the model** — from Python or directly in SQL:
```python
preds = mv.run(input_df, function_name="predict")
```
```sql
SELECT ML_DB.MODELS.churn_clf!PREDICT(feature1, feature2) AS score FROM customers;
```

Registry-logged models can run in the warehouse or, for heavier/GPU models, be **deployed to SPCS** — the two features compose: Registry for lifecycle/versioning, SPCS for container runtime.
