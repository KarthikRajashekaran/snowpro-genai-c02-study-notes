# 2.4 Perform Data Analysis Given a Use Case

Objective 2.2 tests choosing the right approach for a scenario. The decision hinges first on **data type**:

| Data type | Typical approach | Core tools |
|-----------|------------------|-----------|
| **Unstructured** (docs, chat, audio, images) | Parse/extract, or **RAG** (retrieve-then-generate) | `AI_PARSE_DOCUMENT`, `AI_EXTRACT`, `AI_SIMILARITY`, `AI_COMPLETE`, **Cortex Search** |
| **Structured** (tables) | **Text-to-SQL** over a semantic model | `AI_COMPLETE`, **Cortex Analyst** (VQR, custom instructions) |
| **Multimodal** (audio/image) | Transcribe / vision | `AI_TRANSCRIBE`, multimodal `AI_COMPLETE` + `TO_FILE` |

The three foundational patterns:
- **Fully-managed LLM call** — one-shot `AI_COMPLETE`/task functions on the data you already have.
- **RAG** — retrieve relevant chunks (semantic search / Cortex Search) then feed them to `AI_COMPLETE`. Grounds answers in your data and reduces hallucination.
- **Text-to-SQL** — natural-language question → SQL over structured tables via Cortex Analyst.

## Unstructured data

### Document processing functions
- **`AI_PARSE_DOCUMENT`** — OCR/layout-extract PDFs & images in a stage into text/markdown (front door for document RAG).
- **`AI_EXTRACT`** — pull specific fields/answers from text or a document file.
- **`AI_SIMILARITY`** — quick semantic comparison of two texts (one-off relevance scoring).
- **`AI_COMPLETE`** — generate the final answer, summary, or classification.

```sql
-- Parse → extract fields in one pipeline
WITH parsed AS (
    SELECT id,
           AI_PARSE_DOCUMENT(TO_FILE('@contracts', file_name), {'mode':'LAYOUT'}) AS doc
    FROM contract_files
)
SELECT id,
       AI_EXTRACT(text => doc:content::string,
                  responseFormat => ['party_a','party_b','effective_date','total_value']) AS fields
FROM parsed;
```

### RAG with Cortex Search
**Cortex Search** is Snowflake's managed retrieval service (hybrid **vector + keyword** search with **semantic reranking**) that powers RAG and enterprise search without you hand-building an ANN index.

**Build pipeline (indexing side):**
1. **Parse** documents → `AI_PARSE_DOCUMENT` (LAYOUT mode gives markdown).
2. **Chunk** → `SPLIT_TEXT_MARKDOWN_HEADER` (section-aware) or `SPLIT_TEXT_RECURSIVE_CHARACTER` (size-based, with overlap).
3. **Embed** → the service embeds chunks with a chosen **embedding model** (e.g. `snowflake-arctic-embed-l-v2.0`).
4. **Create the search service** over the chunk table.

```sql
CREATE OR REPLACE CORTEX SEARCH SERVICE kb_search
    ON chunk                              -- searchable text column
    ATTRIBUTES doc_id, section            -- filterable metadata
    WAREHOUSE = search_wh
    TARGET_LAG = '1 hour'
    EMBEDDING_MODEL = 'snowflake-arctic-embed-l-v2.0'
    AS
        SELECT chunk, doc_id, section FROM doc_chunks;
```

**Query side** — retrieve top chunks (the service does vector + keyword retrieval then **semantic reranking** to reorder by true relevance), then hand them to `AI_COMPLETE`:

```sql
SELECT AI_COMPLETE('claude-3-5-sonnet',
    CONCAT('Answer using only this context:\n',
           SNOWFLAKE.CORTEX.SEARCH_PREVIEW('kb_search',
              {'query':'What is the SLA credit for downtime?', 'limit':5}):results::string,
           '\nQuestion: What is the SLA credit for downtime?')) AS answer;
```

**Chunking guidance (exam-relevant):**
- **Chunk size** — big enough to be meaningful, small enough to be specific and fit the embedding model's context; a few hundred tokens is typical. Too large dilutes relevance; too small loses context.
- **Overlap** — carry a small overlap (e.g. 10–15%) so ideas spanning a boundary aren't lost.
- **Section-aware** — prefer `SPLIT_TEXT_MARKDOWN_HEADER` so chunks respect document structure.
- **Embedding model** — must be consistent between indexing and querying; pick by language coverage and dimension.
- **Semantic reranking** — a second-stage model reorders initial candidates by relevance, materially improving answer quality over raw vector distance.

### Multi-modal analytics (audio & image)

**Audio → text → analytics:**
```sql
WITH t AS (
    SELECT call_id, AI_TRANSCRIBE(TO_FILE('@calls', file_name)) AS transcript
    FROM call_files
)
SELECT call_id,
       AI_SENTIMENT(transcript:text::string)                          AS sentiment,
       AI_CLASSIFY(transcript:text::string, ['billing','tech','churn']) AS topic
FROM t;
```

**Image analysis** via multimodal `AI_COMPLETE` + `TO_FILE`:
```sql
SELECT sku,
       AI_COMPLETE('claude-3-5-sonnet',
           PROMPT('Does this product image show visible damage? Answer yes/no. {0}',
                  TO_FILE('@product_img', img_path))) AS damage_check
FROM product_photos;
```

## Structured data

### AI_COMPLETE on tabular values
For simple per-row generation over structured columns (enrichment, classification, standardized text), call `AI_COMPLETE`/task functions directly — often with **structured outputs** for typed results (see [2.2](./2.2_Cortex_LLM_Complete_Functions.md)).

### Cortex Analyst (text-to-SQL)
**Cortex Analyst** turns natural-language business questions into governed SQL over a **semantic model / semantic view** (which defines tables, dimensions, measures, relationships, and synonyms). It is the structured-data counterpart to Cortex Search.

Key capabilities to know:
- **Verified Query Repository (VQR)** — a curated set of **verified question → SQL** pairs attached to the semantic model. Analyst uses them as trusted examples, dramatically improving accuracy and consistency on known questions. Add hard/critical queries to the VQR.
- **Integration with Cortex Search** — Analyst can call a Cortex Search service to resolve **literal / high-cardinality dimension values** (e.g. mapping "Coke" → the exact `product_name` string), so filters match real data instead of hallucinated values.
- **Suggested questions** — Analyst can propose sample questions the semantic model can answer, guiding users toward answerable queries.
- **Custom instructions (`CUSTOM_INSTRUCTIONS`)** — natural-language guidance baked into the semantic model (e.g. "fiscal year starts in February", "always exclude test accounts", preferred definitions), steering how SQL is generated.

```yaml
# Sketch of a semantic model consumed by Cortex Analyst
name: sales_analytics
tables:
  - name: orders
    dimensions: [region, product_name, order_date]
    measures:   [revenue, order_count]
    synonyms:   {revenue: [sales, turnover]}
custom_instructions: >
  Fiscal year starts Feb 1. Exclude rows where is_test = TRUE.
verified_queries:
  - question: "What was total revenue by region last fiscal year?"
    sql: SELECT region, SUM(revenue) ...
cortex_search_services:
  - service: product_name_search      # resolves literal product values
    column: product_name
```

Cortex Analyst is invoked via its REST API (and surfaced in Streamlit apps / Snowflake Intelligence — see [2.5](./2.5_Chat_Interfaces_and_Pipelines.md)).

## Performance considerations

Choosing a model and configuration is a scored topic.

### Latency & model size
- Smaller models (`llama3.1-8b`, `mistral-7b`) = **lower latency, lower cost**, good for high-volume simple tasks.
- Larger models (`llama3.1-405b`, `claude-3-5-sonnet`, `mistral-large2`) = **higher accuracy on complex reasoning**, higher latency/cost.
- Start small; escalate only where quality requires it. Batch where possible.

### Accuracy — fine-tuning & reducing hallucinations
- **Fine-tuning** (Cortex Fine-Tuning) adapts a base model to your domain/format from labeled examples — raising accuracy and consistency for a specialized task, often letting a **smaller** fine-tuned model match a larger general one (cheaper + faster).
- **Reduce hallucinations** by grounding: use **RAG** (Cortex Search) so answers cite retrieved context; use **structured outputs** to constrain format; lower `temperature`; and add **verified queries** (VQR) for Cortex Analyst.

### Model capability
- Match the model to the modality and task: multimodal (image) needs a vision-capable model; long documents need a large context window; multilingual needs a multilingual model. Don't pay for capability the task doesn't need.

### Provisioned Throughput
- Default Cortex usage is **on-demand** (shared capacity, pay per token). **Provisioned Throughput** reserves dedicated capacity for a model, giving **predictable latency and guaranteed throughput** for steady, high-volume production workloads. Choose it for scale/SLA — not as a way to save money on small/bursty usage (on-demand is cheaper there).
