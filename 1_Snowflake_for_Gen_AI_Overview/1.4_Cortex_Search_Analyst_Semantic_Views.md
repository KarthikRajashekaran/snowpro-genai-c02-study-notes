# 1.4 Cortex Search, Analyst & Semantic Views

Two of the most heavily tested Cortex features sit at opposite ends of the data spectrum:

- **Cortex Search** — retrieval over **unstructured** text (the engine behind RAG).
- **Cortex Analyst** — natural-language **text-to-SQL** over **structured** data, powered by semantic models / Semantic Views.

Understanding when to use each, and how they are configured, is core to Domain 1.

---

## Part A — Cortex Search

### What it is
Cortex Search is a **fully managed retrieval service** for unstructured/text data. You point it at a source table (or view) of text; Snowflake handles chunk indexing, embedding, and low-latency retrieval. It performs **AI hybrid search** — combining **semantic (vector) similarity** with **keyword/lexical search** and reranking — so it returns relevant results even when wording differs from the query.

### Primary use cases
- **RAG (Retrieval-Augmented Generation)** — retrieve the most relevant passages to ground an LLM's answer and reduce hallucination.
- **Unstructured-data use cases** — enterprise search over documents, knowledge bases, support tickets, chat logs, product catalogs, contracts, and other text.
- **Chat / Q&A assistants** that must cite source documents.

### AI hybrid search concept
"Hybrid" means the service does **not** rely on vector similarity alone. It fuses:
1. **Semantic search** — dense vector embeddings capture meaning.
2. **Lexical / keyword search** — exact term and phrase matching for names, IDs, codes.
Results from both are merged and **reranked**, giving better recall and precision than either method alone.

### Creating a search service
```sql
CREATE OR REPLACE CORTEX SEARCH SERVICE support_docs_search
  ON chunk                        -- the text column to search
  ATTRIBUTES product, region      -- filterable metadata columns
  WAREHOUSE = search_wh
  TARGET_LAG = '1 hour'           -- how fresh the index stays vs. base data
  AS (
    SELECT chunk, product, region, source_url
    FROM knowledge_chunks
  );
```

### Multi-index queries
A single query can span **multiple Cortex Search services (indexes)** so an application can retrieve from several corpora at once (for example, product docs + release notes + support KB) and merge the results. This is useful when relevant knowledge is spread across separate services rather than one table. Multi-index retrieval is typically orchestrated through the application layer or through **Cortex Agents**, which can call more than one search service as tools.

### Access-control requirements
- The caller needs the **`SNOWFLAKE.CORTEX_USER`** database role to use Cortex features.
- Additional privilege is required to **use a specific search service** (e.g., `USAGE` on the service and its schema/database).
- The service reads the **source data at index time using the privileges of its owner**, so grant carefully — anyone allowed to query the service can retrieve content derived from the indexed rows.
- Apply row/column governance (row access policies, masking) on the **source** data; design services so users only reach content they're entitled to (e.g., separate services per audience, or filter with `ATTRIBUTES`).

### Different ways to use Cortex Search
- **SQL** — query the service with the search preview/query function to get ranked results.
- **Python API** (Snowpark / `snowflake` Python client) — for app back-ends and pipelines.
- **REST API** — call the service from external applications and chatbots.
- **Cortex Agents** — Search is exposed as a retrieval **tool** an agent can call (see [1.5](./1.5_Agents_Intelligence_and_Code.md)).
- **Snowsight / AI Studio** — create, preview, and test a service without code.

```sql
-- Query a search service from SQL (returns ranked, optionally filtered results)
SELECT *
FROM TABLE(
  CORTEX_SEARCH_DATA_SCAN(
    SERVICE_NAME => 'support_docs_search'
  )
)
LIMIT 5;
-- In practice you call the service's query function/REST endpoint with a natural-language
-- query string and optional attribute filters; syntax evolves, so confirm in current docs.
```

## Part B — Cortex Analyst

### What it is
Cortex Analyst is a **text-to-SQL** service. A business user asks a question in natural language; Analyst generates and runs **SQL** against your governed tables, then returns the answer (and the SQL it used). It is exposed primarily through a **REST API**, so it is typically embedded in apps, dashboards, and chat experiences.

### Text-to-SQL use cases
- Self-service analytics — "What was net revenue by region last quarter?"
- Conversational BI inside internal apps.
- A **structured-data tool** for Cortex Agents (Analyst answers the "numbers" questions; Search answers the "documents" questions).

### Semantic Models & Semantic Views (the grounding)
Analyst does not guess your schema — it is grounded by a **semantic layer** that defines tables, columns, relationships, **dimensions**, **metrics/measures**, synonyms, and descriptions in business terms. This can be supplied two ways:

1. **YAML semantic model specification** — a YAML file (often stored on a stage) describing logical tables, dimensions, measures, relationships, synonyms, and verified queries.
2. **Semantic View** — a **native Snowflake object** (`CREATE SEMANTIC VIEW`) that encodes the same semantics as a first-class, governed database object rather than a file.

Both give Analyst the vocabulary to map business language to correct SQL.

```sql
-- Semantic View: a native object encoding logical tables, relationships, dimensions, metrics
CREATE OR REPLACE SEMANTIC VIEW sales_sv
  TABLES (
    orders AS analytics.public.orders PRIMARY KEY (order_id),
    customers AS analytics.public.customers PRIMARY KEY (customer_id)
  )
  RELATIONSHIPS (
    orders (customer_id) REFERENCES customers (customer_id)
  )
  DIMENSIONS (
    customers.region AS region,
    orders.order_date AS order_date
  )
  METRICS (
    orders.net_revenue AS SUM(orders.amount) COMMENT = 'Net revenue'
  );
-- Note: exact clause syntax evolves; validate against current Snowflake docs.
```

### Semantic Views Autopilot
**Autopilot** accelerates building a semantic view: Snowflake inspects your tables and **auto-generates a starter semantic model** — proposing dimensions, metrics, relationships, synonyms, and descriptions — which you then review and refine. It lowers the effort of standing up Cortex Analyst on a new dataset.

### YAML specification for semantic views
The YAML spec is the portable, file-based way to define the semantic model. Key sections typically include:
- **tables / logical tables** and their base physical tables
- **dimensions** (categorical/time attributes)
- **measures / metrics** (aggregations expressed in business terms)
- **relationships** (joins between logical tables)
- **synonyms** (alternate business phrasings that map to a column/metric)
- **verified_queries** (see below)
- **custom instructions** (see below)

A YAML model can be converted to / from a native Semantic View, and Snowsight/AI Studio can generate and validate it for you.

### Verified Query / Verified Query Repository (VQR)
A **Verified Query** is a natural-language question paired with a **known-correct SQL answer**, reviewed and marked trusted. The collection of these is the **Verified Query Repository (VQR)**. Analyst uses verified queries as high-confidence examples to:
- return the vetted SQL for matching/near-matching questions, and
- steer generation toward your organization's correct patterns.
This improves accuracy and consistency and is a primary lever for tuning Analyst quality.

### Custom Instructions
**Custom Instructions** are natural-language guidance attached to the semantic model that shape how Analyst behaves — e.g., default filters ("exclude test accounts"), preferred definitions ("revenue means net of refunds"), formatting, or business rules. They let you encode organization-specific conventions without changing the underlying schema.

### Cortex Analyst REST API
Analyst is consumed mainly via its **REST API**: the app sends the user's question plus a reference to the semantic model (YAML on a stage or a Semantic View), and receives the generated SQL and/or results. This makes it easy to embed conversational analytics in custom apps and is how **Cortex Agents** invoke Analyst as a tool.

### Agentic semantic model text-to-SQL
Beyond single-shot generation, Analyst supports an **agentic** approach: the model can reason in multiple steps over the semantic model — decomposing a complex question, choosing metrics/dimensions, applying verified queries and custom instructions, and iterating — to produce more reliable SQL for harder questions. Within a Cortex Agent, this is the "structured-data reasoning" capability that complements Cortex Search's retrieval.

## Search vs Analyst — quick contrast

| | **Cortex Search** | **Cortex Analyst** |
|---|---|---|
| Data | Unstructured text | Structured tables |
| Job | Retrieve relevant passages | Generate & run SQL |
| Powers | RAG, enterprise search | Conversational BI / text-to-SQL |
| Grounded by | Indexed source table + embeddings | Semantic model (YAML) or Semantic View |
| Main interface | SQL / Python / REST / agent tool | REST API / agent tool |
