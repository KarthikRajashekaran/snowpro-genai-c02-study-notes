# 1.6 Bringing Your Own Models

Beyond the hosted Cortex models, Snowflake lets you **bring your own** and **open-source** models into the platform — training, logging, deploying, and serving them next to your governed data. The three pillars are the **Model Registry**, **Snowpark Container Services (SPCS)**, and **Cortex Fine-tuning**.

---

## Snowflake Model Registry

### Overview
The **Model Registry** is a Snowflake-native repository (part of Snowpark ML) for **managing, versioning, and deploying ML/AI models** as first-class, governed schema-level objects (`MODEL` objects). It gives models the same RBAC, lineage, and governance as your data, and lets you **call a model directly from SQL or Python** once registered.

### Bring-your-own-model types
The registry supports many model "flavors," including:
- **scikit-learn, XGBoost, LightGBM** and other classic ML models
- **PyTorch / TensorFlow** deep-learning models
- **Hugging Face / open-source LLMs and transformers**
- **Snowpark ML** modeling pipelines
- **Custom models** — arbitrary Python logic wrapped in a **custom model** class (`custom_model.CustomModel`) when your model doesn't fit a built-in flavor

This is how you run **open-source and custom** models inside Snowflake rather than the hosted Cortex catalog.

### Logging (registering) a model
```python
from snowflake.ml.registry import Registry

reg = Registry(session=session, database_name="ML_DB", schema_name="MODELS")

mv = reg.log_model(
    model=my_trained_model,          # e.g., an sklearn/xgboost/HF/custom model
    model_name="churn_classifier",
    version_name="v1",
    conda_dependencies=["scikit-learn"],
    sample_input_data=sample_df,     # used to infer the signature
    comment="Churn model v1",
)
```

### Calling a model
```python
# Python: run inference through the registered model version
preds = mv.run(input_df, function_name="predict")
```
```sql
-- SQL: models registered in the registry can be invoked as objects
SELECT churn_classifier!predict(feature1, feature2) AS score
FROM customers;
-- (invocation syntax depends on the registered functions/signature)
```

### Snowsight UI
The Model Registry is browsable in **Snowsight**: view registered models, their **versions**, signatures, metrics, and metadata, set the **default version**, and manage the model lifecycle through the UI in addition to Python/SQL.

### Where models run
Registered models can be served on **warehouse compute** (for many CPU model types) or on **Snowpark Container Services** with GPUs for large deep-learning/LLM inference (see below).

## Snowpark Container Services (SPCS)

### What it is
**Snowpark Container Services** is a fully managed **container runtime inside Snowflake**. It runs your own **Docker/OCI images** on Snowflake-managed infrastructure (including **GPU** options), so you can host custom model servers, LLMs, APIs, and full applications next to your data without moving it out. It is the compute layer for **large / GPU-bound bring-your-own models**.

### Core building blocks
- **Environment / setup** — a database, schema, and roles; grant the privileges to create compute pools and services.
- **Docker images** — you build a container image with your model + serving code.
- **Image repository** — a Snowflake-managed **OCI registry** (`CREATE IMAGE REPOSITORY`) you push images to.
- **Compute pool** — the pool of (optionally GPU) nodes your containers run on (`CREATE COMPUTE POOL`).
- **Service spec file** — a **YAML specification** describing the container(s): image, endpoints, ports, resources, env vars, volumes.
- **Service / job** — a long-running **service** (`CREATE SERVICE`) or a one-off **job** created from the spec.

```sql
-- 1) Create an image repository to push your Docker image to
CREATE IMAGE REPOSITORY ml_db.models.repo;

-- 2) Create a compute pool (optionally GPU-enabled) to run containers
CREATE COMPUTE POOL model_pool
  MIN_NODES = 1
  MAX_NODES = 2
  INSTANCE_FAMILY = GPU_NV_S;   -- instance families vary by region

-- 3) Create a service from a spec YAML (uploaded to a stage)
CREATE SERVICE ml_db.models.llm_service
  IN COMPUTE POOL model_pool
  FROM @ml_db.models.specs
  SPECIFICATION_FILE = 'llm_service.yaml';
```

```yaml
# llm_service.yaml — service specification (shape; confirm fields in current docs)
spec:
  containers:
    - name: model-server
      image: /ml_db/models/repo/my-llm:latest
      env:
        MODEL_NAME: my-open-source-llm
      resources:
        requests:
          nvidia.com/gpu: 1
  endpoints:
    - name: api
      port: 8080
      public: false
```

### Typical BYO-model flow on SPCS
1. Build a Docker image with your model + inference server.
2. Push it to a Snowflake **image repository**.
3. Create a **compute pool** (GPU if needed).
4. Write a **service spec YAML** and `CREATE SERVICE`.
5. Call the service's endpoint from SQL/UDFs/apps — data never leaves Snowflake.

> The Model Registry can **deploy to SPCS** under the hood for GPU inference, so the two features work together: the registry manages the model, SPCS provides the container compute.

## Cortex Fine-tuning [Public Preview]

### What it is
**Cortex Fine-tuning** lets you **customize a supported base LLM** on your own labeled examples (parameter-efficient fine-tuning) to improve quality on a specific task — often letting a smaller, cheaper model match a larger one on your use case. It is serverless: you supply training data (prompt/response pairs) and Snowflake produces a **fine-tuned model** you then call like any Cortex model.

### How it's used
- Run through the **`SNOWFLAKE.CORTEX.FINETUNE`** function (create/describe/list/cancel a fine-tuning job) or via **AI Studio** in Snowsight.
- Training and validation data come from Snowflake **tables** (columns of prompts and target completions).
- The resulting customized model is invoked with the standard completion functions (e.g., `AI_COMPLETE` / `COMPLETE`) by its fine-tuned model name.

```sql
-- Kick off a fine-tuning job (Public Preview; confirm exact arguments in current docs)
SELECT SNOWFLAKE.CORTEX.FINETUNE(
  'CREATE',
  'my_finetuned_model',            -- name for the resulting model
  'llama3.1-8b',                   -- supported base model
  'SELECT prompt, completion FROM training_data',    -- training query
  'SELECT prompt, completion FROM validation_data'   -- validation query
);
```

### When to choose what
| Need | Use |
|---|---|
| Use a hosted model as-is | Cortex Models & Functions (1.1/1.2) |
| Improve a base model on your task/style | **Cortex Fine-tuning** |
| Run your own trained ML/DL/HF/custom model | **Model Registry** |
| Host a large/GPU model or custom server/app | **Snowpark Container Services** |
