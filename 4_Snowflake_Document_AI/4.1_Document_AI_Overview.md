# 4.1 Document Parsing & Extraction Functions

## Overview

Snowflake Document Processing (C02) is built on two Cortex AISQL functions that read files directly from a stage:

- **`AI_PARSE_DOCUMENT`** — converts a document into **text** (OCR mode) or **structured markdown** (LAYOUT mode). Use it to make document content readable, chunkable, and searchable.
- **`AI_EXTRACT`** — pulls **structured fields** out of a document (or text) according to a **schema / response format** you define. Use it to turn a document into typed columns.

> The legacy `DOCUMENT_AI.CLASSIFY()`, `DOCUMENT_AI.OCR()`, and `DOCUMENT_AI.EXTRACT_TABLES()` functions referenced in older material **do not exist**. The C02 exam tests `AI_PARSE_DOCUMENT` and `AI_EXTRACT`.

**Two-line decision guide:**
- Need the *content* (text or markdown) of a document? → **`AI_PARSE_DOCUMENT`**
- Need specific *values* (vendor, total, dates, line items)? → **`AI_EXTRACT`**

## AI_PARSE_DOCUMENT

`AI_PARSE_DOCUMENT` reads a file from a stage and returns an OBJECT containing the extracted content plus metadata.

### Syntax

```sql
SELECT AI_PARSE_DOCUMENT(
    TO_FILE('@my_stage', 'documents/contract.pdf'),
    {'mode': 'LAYOUT', 'page_split': TRUE, 'page_limit': 10}
) AS parsed;
```

- **First argument** — a `FILE` value referencing the staged document (via `TO_FILE(stage, relative_path)` or a directory-table `FILE` column).
- **Second argument** — an OBJECT of options: `mode`, `page_split`, `page_limit`.

### Mode: OCR vs LAYOUT

| Mode | Output | Use when |
|------|--------|----------|
| **`OCR`** (default) | **Raw text** — a continuous text stream with no structural markup | You just need the text; structure/tables don't matter; scanned/simple documents |
| **`LAYOUT`** | **Markdown** that **preserves tables, headings, lists, and reading order** | You need to keep document structure — tables, sections — as searchable markdown (e.g. contracts, structured reports) |

**Exam mapping:** *"preserve the structure of contracts as searchable markdown"* → **LAYOUT** mode. *"extract raw text from a scanned image"* → **OCR** mode.

```sql
-- OCR mode: raw text from a scanned document
SELECT AI_PARSE_DOCUMENT(
    TO_FILE('@doc_stage', 'scans/receipt.png'),
    {'mode': 'OCR'}
):content::STRING AS raw_text;

-- LAYOUT mode: structure-preserving markdown from a contract
SELECT AI_PARSE_DOCUMENT(
    TO_FILE('@doc_stage', 'contracts/msa.pdf'),
    {'mode': 'LAYOUT'}
):content::STRING AS markdown_content;
```

### page_split

`page_split` controls whether output is returned as **one blob** or **per page**.

- `page_split => FALSE` (default): a single `content` string for the whole document.
- `page_split => TRUE`: `content` is returned per page (an array of page objects), so you can process, chunk, or cite by page.

```sql
-- Return per-page markdown, then flatten one row per page
SELECT
    p.index + 1                       AS page_number,
    p.value:content::STRING           AS page_markdown
FROM (
    SELECT AI_PARSE_DOCUMENT(
        TO_FILE('@doc_stage', 'contracts/msa.pdf'),
        {'mode': 'LAYOUT', 'page_split': TRUE}
    ) AS parsed
),
LATERAL FLATTEN(input => parsed:pages) AS p;
```

### page_limit

`page_limit` caps how many pages are processed — a key **cost and performance** control for large documents.

```sql
-- Only process the first 5 pages
SELECT AI_PARSE_DOCUMENT(
    TO_FILE('@doc_stage', 'reports/annual_report.pdf'),
    {'mode': 'LAYOUT', 'page_limit': 5}
) AS parsed;
```

### Response shape

`AI_PARSE_DOCUMENT` returns an OBJECT. Typical fields:

```json
{
  "content": "…full text or markdown… (or per-page array when page_split=TRUE)",
  "metadata": { "pageCount": 12 }
}
```

Cast out what you need with the `:` path operator and `::` type cast:

```sql
SELECT
    parsed:content::STRING              AS body,
    parsed:metadata:pageCount::INT      AS page_count
FROM ( SELECT AI_PARSE_DOCUMENT(TO_FILE('@doc_stage','file.pdf')) AS parsed );
```

## AI_EXTRACT

`AI_EXTRACT` extracts **structured fields** from a document or text. You provide a **response format** — a set of fields (or natural-language questions) — and Cortex returns the answers as a structured OBJECT.

### Syntax

```sql
SELECT AI_EXTRACT(
    file        => TO_FILE('@doc_stage', 'invoices/inv_001.pdf'),
    responseFormat => {
        'vendor_name'   : 'What is the vendor or supplier name?',
        'invoice_total' : 'What is the total amount due?',
        'invoice_date'  : 'What is the invoice date?',
        'line_items'    : 'List each line item with description, quantity, and amount'
    }
) AS extracted;
```

- **`file`** (or `text`) — the source: a staged `FILE`, or a text column (e.g. output of `AI_PARSE_DOCUMENT`).
- **`responseFormat`** — the **schema**: a set of named fields, each described by the question/instruction that defines it. The keys become the output field names.

### Extracting structured fields from invoices

```sql
-- One structured row per invoice
SELECT
    file_name,
    extracted:vendor_name::STRING    AS vendor,
    extracted:invoice_total::STRING  AS total,
    extracted:invoice_date::STRING   AS invoice_date,
    extracted:line_items             AS line_items
FROM (
    SELECT
        relative_path AS file_name,
        AI_EXTRACT(
            file => TO_FILE('@invoice_stage', relative_path),
            responseFormat => {
                'vendor_name'   : 'Vendor or supplier name',
                'invoice_total' : 'Total amount due, numbers only',
                'invoice_date'  : 'Invoice date in YYYY-MM-DD',
                'line_items'    : 'Array of line items with description, quantity, unit price, amount'
            }
        ) AS extracted
    FROM DIRECTORY(@invoice_stage)
);
```

**Exam mapping:** *"extract structured fields (vendor, total, line items) from invoices"* → **`AI_EXTRACT`** with a **schema / response format**.

### Response format

The `responseFormat` argument is what makes the output **structured and predictable**. Each entry names an output field and describes what to pull. Design tips:

- Use clear, unambiguous field names (`invoice_total`, not `amt`).
- Describe the exact form you want (e.g. "numbers only", "YYYY-MM-DD", "as an array").
- Group repeating data (line items, parties) into an array field.

### How to prompt / prompt engineering

`AI_EXTRACT` accuracy depends heavily on how you phrase each field's instruction. Best practices:

1. **Be specific about the target** — "Total amount due including tax" beats "amount".
2. **Constrain the format** — ask for a date format, currency, numbers-only, or an array explicitly.
3. **Disambiguate look-alikes** — distinguish "invoice date" from "due date", "subtotal" from "total".
4. **Ask for structure when data repeats** — request an array of objects for line items or signatories.
5. **Handle missing data** — instruct it to return null/empty when a field is absent, to avoid hallucinated values.
6. **Prefer parse-then-extract for complex docs** — run `AI_PARSE_DOCUMENT` in LAYOUT mode first, then `AI_EXTRACT` on the resulting markdown so tables are already structured.

```sql
-- Parse (LAYOUT) then extract from the markdown for higher accuracy on tabular docs
WITH parsed AS (
    SELECT
        relative_path,
        AI_PARSE_DOCUMENT(
            TO_FILE('@contract_stage', relative_path),
            {'mode': 'LAYOUT'}
        ):content::STRING AS md
    FROM DIRECTORY(@contract_stage)
)
SELECT
    relative_path,
    AI_EXTRACT(
        text => md,
        responseFormat => {
            'party_a'      : 'Name of the first contracting party',
            'party_b'      : 'Name of the second contracting party',
            'effective_date': 'Contract effective date in YYYY-MM-DD',
            'term_length'  : 'Contract term or duration',
            'auto_renew'   : 'Does the contract auto-renew? Answer true or false'
        }
    ) AS fields
FROM parsed;
```

## Parsing vs Extraction — quick reference

| Task | Function | Key options |
|------|----------|-------------|
| Text of a scanned document | `AI_PARSE_DOCUMENT` | `mode => 'OCR'` |
| Structure-preserving markdown (tables, headings) | `AI_PARSE_DOCUMENT` | `mode => 'LAYOUT'` |
| Per-page output for chunking/citation | `AI_PARSE_DOCUMENT` | `page_split => TRUE` |
| Limit pages processed (cost control) | `AI_PARSE_DOCUMENT` | `page_limit => N` |
| Typed fields (vendor, total, line items) | `AI_EXTRACT` | `responseFormat` schema |
| Higher accuracy on complex/tabular docs | Parse (LAYOUT) → `AI_EXTRACT` | chain both |

## Study Questions

1. **Which `AI_PARSE_DOCUMENT` mode preserves tables and document structure as markdown?**
   - A) OCR
   - B) LAYOUT
   - C) TABLE
   - D) STRUCTURED

2. **You need to extract the vendor, total, and line items from a batch of invoices as typed fields. Which function do you use?**
   - A) `AI_PARSE_DOCUMENT` in OCR mode
   - B) `AI_EXTRACT` with a response format
   - C) `DOCUMENT_AI.EXTRACT_TABLES()`
   - D) `SUMMARIZE()`

3. **Which option makes `AI_PARSE_DOCUMENT` return content page-by-page?**
   - A) `page_limit`
   - B) `page_split`
   - C) `mode => 'PAGES'`
   - D) `split_pages`

4. **What limits the number of pages `AI_PARSE_DOCUMENT` processes (a cost lever for large files)?**
   - A) `page_split`
   - B) `max_rows`
   - C) `page_limit`
   - D) `row_limit`

5. **Which is the best prompt-engineering practice for `AI_EXTRACT`?**
   - A) Use short, vague field names to keep it flexible
   - B) Constrain the output format (e.g., date as YYYY-MM-DD, numbers only) and ask for arrays when data repeats
   - C) Always process the full document with no schema
   - D) Extract every possible field to be safe

**Answers: 1-B, 2-B, 3-B, 4-C, 5-B**
